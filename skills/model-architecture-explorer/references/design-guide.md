# 架构探索器的阅读与视觉质量

用于设计完整新页面、改造既有页面或对照用户给出的参考页面。先看参考的真实渲染和交互，再决定哪些结构应保留；不能只从 HTML 是否存在、按钮是否能点来判断成品质量。

## 先建立阅读层次

- **模型概览**：模型名称、用一句话说明的核心思路、实际配置的关键参数。参数卡优先显示输入规模、特征宽度、交互深度、输出空间等对理解有用的信息。不要把源码文件数等工具统计冒充模型参数。
- **架构工作区**：整体图是主要阅读入口。分组、颜色、分支与连线说明数据依赖；旁边的检查器补充选中模块的说明、形状、参数和源码。图和检查器应有清晰的视觉主次。
- **深入解释**：核心机制的 LaTeX 公式、容易误读的实现要点、按前向路径排列的张量形状表。它们解释图为什么这样画，而不是重复模块标题。
- **逐层查看**：整体模块进入内部计算图，算子进入详情，详情进入源码。相同层的实例选择、已有的形状参数和演示功能应保留，并核对其联动行为。

按模型和用户任务调整内容，不必硬凑卡片数。已有高质量页面时优先局部修改；不要为了适配标准 spec 而删掉有用的阅读区、层选择器、控制项或特有布局。

## 图的密度与排版

总览和细图是两种不同的阅读任务。总览应让读者区分原始输入、编码特征、融合结果与解码输出，必要时分成阶段列；不要把原始输入和整条编码链全部收进一个大卡片。核心细图应让读者回答“这个结果如何由输入算出来”，而不是再次看到总览模块的目录。

例如双路注意力，适合把两路输入放在两列，每侧用一个节点合并归一化与投影，中间汇合评分矩阵，再分到两个 softmax 和跨路 Value 读取。Value 旁路、转置关系与残差底座是解释的主体；不必为每个 LN、投影和 Add 各造一个大卡片。具体投影是否共享、哪一路继续做自注意力，都从目标源码确认。

判断粒度是否合适：读者在当前核心细图中能否指出主要中间张量、分支汇合点和更新方向，而无需跳到多个子图中记忆拼接。公式不能全部藏进弹窗；图上保留决定数据关系的短公式，详情解释完整计算与边界条件。继续下钻用于更深的实现细节。

- 先按输入、编码、交互、解码等真实阶段组织布局，再为每个节点安排位置。关键分支、残差与条件注入应能沿线追踪，避免把所有模块排成相同大小的长列表。
- 节点宽高由标题、实际正文与公式高度、行距和内边距决定。普通纯文本节点可先按左右 14–18 px、底部 14–20 px 的内边距估算，再用渲染结果调整；不要把短文本节点拉高到与多行节点相同。检查文字最末一行到块底的距离，出现超过一两行的无用途空白时，收紧块高并同步调整边线和画布。只有容纳分支、分组或交互控件时才预留额外空间。
- 大模块可使用 `blocks` / `badge` / `foot` 展示内部摘要与重复次数；下钻后再解释完整算子。连线不要穿过节点，旁路要有足够间距。
- 总览节点只放名称、关键配置和关键形状。详细的公式、说明和源码放入细图或详情；适合直接解释计算关系的图内公式可以使用 LaTeX，并为实际渲染高度预留空间。
- 不把整张长图一味缩小到屏幕里。保持可读字号，使用内部滚动、缩放和有意义的视图拆分。手机上不让页面整体横向溢出。
- 算子图保持可读字号，但不能把加大画布和延长页面作为默认解决方式。先合并连续步骤、压缩多余空行，再按模型的分支结构排成紧凑行列。声明式模板的 `variant: "operator"` 只是字号选项；布局方法与替代公式渲染见 [compact-diagrams.md](compact-diagrams.md)。
- 颜色稳定对应数据流或计算阶段；浅背景、边框与留白辅助分组，不用装饰替代结构。

## 形状与前向演示

模板支持 `stats`、`mechanism`、`notes`、`trace`、`controls`、`dimensions` 和视图 `flow`，格式见 [page-spec.md](page-spec.md)。

- 只有在已核对的关系确实会随参数变化时才提供控制项。改变 batch、序列长度或模型配置后，参数卡、图内形状、检查器、机制说明与张量表应保持一致。
- `flow` 显式声明前向步骤；并行或逻辑上同阶段的模块可以共同高亮。不能根据图上从左到右的位置自动推断真实执行顺序。
- 前向演示只说明信息依赖，不表示计算耗时、设备调度或实际执行了模型。

## 导航与参考保真

主标签对应主要理解任务，使用视图 `parent` 把投影内部、单头计算等子图归入适合的父级；通过面包屑与返回保留上下文。不要把每个源码类都提升为同级导航。重复层选择器只在相关视图出现，切换时更新实例说明、形状及其前后层关系。

有参考页时，先记录其总览阶段、核心细图中的计算节点与关键边线、参数控件、源码路径和下方解释区。随后确认哪些应保留、哪些需按当前源码纠正。参考的 HTML 已能表达这些关系时，优先改造原页面；迁移到 spec 是可选实现方式。不能把“看起来用了相同颜色和卡片”当作保真。

## 用同一组内容验证

1. 比较用户参考与结果时，尽量使用同一个模型、配置和数据密度。一个只有一两个节点的示意 spec 不能证明复杂模型的页面质量。
2. 实际查看桌面总览、内部计算图、算子详情和手机布局的截图。逐块检查文本与块的比例、底部空白和节点间距，不能只检查文字是否溢出。检查文字是否被裁切、图是否过小、长公式是否遮挡相邻算子、侧栏是否挤压主图，以及下方说明是否仍然完整。
3. 检查配置、形状参数、层实例和演示的联动。验证导出的 SVG 在单独打开时仍保留图内公式、字体与正确尺寸。
4. 检查脚本通过后仍需看截图。自动检查能发现交互和边界错误，不能代替对信息组织、视觉层次与解释质量的判断。

一个已出现的失败模式是：参考只有少量主视图，但内部画出了两路投影、softmax 与 Value 旁路；重建页拥有更多标签和更多文字，却每图只剩几个抽象框。此时应修复计算的可见性与导航粒度，增加模块数或美化卡片并不能补回解释能力。

相反的失败模式是把“细化”理解为所有调用都独立成框，导致 LN、QKV、softmax、读取、投影、Dropout、残差构成长链，相同形状和说明反复出现。此时将连续步骤合成计算单元，逐算子明细放到点击详情；不要继续扩大画布或缩小文字。

参考页的模型参数和源码属于那个模型；只复用设计原则，不把其专用数据写进通用模板。
