# 模型架构交互可视化

把模型源码转成读者可以逐步展开的架构网页。图中的连接、执行顺序、张量形状和配置区别应能由当前工作区代码解释。使用用户的语言，沿用已有页面的设计与技术栈；新建且无特别要求时，优先离线可用的 HTML + SVG + JavaScript。

## 从代码建立结构

- 先检查工作区说明与未提交修改。找到模型构建入口、`forward`、配置 dataclass / YAML、训练与推理适配层，再沿真实调用链读取各组件。README 和论文用于背景，当前源码用于确认实现。
- 梳理输入预处理、编码、特征投影、位置编码、交互 / 融合、状态或条件注入、解码、输出变换。区分模型内操作与模型外归一化、采样和 rollout；不要把一个模型的阶段强加给另一个模型。
- 分别核对库默认值、训练配方、checkpoint 覆盖值；说明页面实际展示哪一种。配置切换应联动形状、实例名称、层数和算子说明，不只改变标题。
- 推导关键形状，写明符号和 padding / patch / horizon 等假设。编码特征宽度、attention 内部宽度、head 数与 head dim 可能不同。检查残差的真实底座、Pre-/Post-Norm、softmax 维度、mask、共享参数与独立层参数。
- 不必加载大模型权重来解释代码。没有执行推理时，将形状标为推导结果；动画只表示信息依赖，不代表实际耗时或 GPU 调度。

## 设计真正的逐层展开

用户提供已有网页或截图时，先检查其真实布局与交互，以它为质量基准，优先局部改进。新建完整页面或改动整体设计时，阅读 [references/design-guide.md](references/design-guide.md)：保留模型概览、关键参数、架构工作区、核心机制、实现要点和张量追踪之间的阅读层次，按实际模型取舍；不要将高质量页面降成只有通用节点和侧栏的演示骨架。

先确定各视图要回答的问题、计算粒度与主要分支，再写 spec。已有高质量参考 HTML 时，优先保留其布局和绘图逻辑，补充源码与交互；不要仅因自带构建器方便而重新套模板。若确需重建，先对照同一配置的总览和核心细图，列明将保留的计算节点、分支、控制项及阅读区。配色相似、卡片齐全和视图数量更多，都不能证明解释能力相当。

按模型复杂度选择视图数量：整体图说明主要数据依赖；模块细图展示紧凑的计算关系；点击详情再给逐算子步骤、配置 / 层实例与源码入口。图的节点对应读者要理解的计算单元，不必一一对应源码调用。

节点尺寸按实际内容确定：先确定可读字号、行数与内边距，再设置宽高；短节点可以更小，不为对齐把只有一两行文字的节点拉成大卡片。若文字集中在上半部、下半部大面积空白，先收紧节点和相关连线，再缩短画布；不要靠整体缩放或填充无关文字解决。排版调整须覆盖所有可下钻的内部视图及配置，逐图核对节点和留白；只压缩总览不能算完成。

先画紧凑示意图：例如将 LN、线性投影和 split heads 合为“归一化与投影”，将 LN → Attention → Dropout → Add 合为一个有残差公式的子层，将多层动作 MLP 合为一个节点。保持 Q/K 与 Value 的实际流向、归一化方向和条件输入可追踪；重复操作、相同形状与配置说明不必逐框重写。细节可用算子弹窗中的折叠步骤保留。只有用户明确要逐算子全展开图时，才将这些步骤分别放到主画布。

有参考页时，以同宽截图比较图高、节点密度和空白比例；不能靠缩小整张图来缩短页面。若结果明显更长，先合并相关步骤、调整行列与缩短文案，再继续制作。紧凑布局与公式排版的方法见 [references/compact-diagrams.md](references/compact-diagrams.md)。

交互契约应直接可见：

- 整体图中标为“点击展开”的模块，单击就进入对应内部计算图；提供返回与清晰的当前视图标记。
- 细图中的可点击算子，单击打开明显的详情弹窗或内联展开区。仅悄悄更新右侧检查器，不足以兑现“展开”。检查器可以辅助展示，并提供显式展开按钮。
- 下钻后保留模块边界的输入与输出：明确每个外部输入在父图中的来源、名称和形状，并映射到图内具体入口；输出说明返回父图后接到哪里。内部生成的噪声、时间索引或位置编码要与外部输入区分，不能让读者靠猜测补全。重复层切换后，输入来源也应从编码器更新为上一层。
- 同结构的多层可使用层号选择器，但要说明结构相同、参数是否独立，并更新实例路径。中间解码层的输入是上一层特征，不能始终画成原始查询直接输入每一层。
- 长图需要可读的文字、内部滚动或放大方式。键盘可激活模块、关闭弹窗；移动端不要让整个页面横向溢出。

## 制作网页与源码映射

未指定交付位置时，页面保存为模型工作区的 `visualization/<model-slug>-architecture.html`，例如 `visualization/evo1-architecture.html`：一层目录加文件名，保持二级路径。`<model-slug>` 使用可辨识的小写模型名；不要默认再套 `architecture/` 子目录，也不要用 `index.html` 作架构页文件名。`visualization/` 的直属文件只保留架构 HTML；spec、定制模板、截图、构建脚本、源码快照和验证记录等辅助文件统一放进同名子目录 `visualization/<model-slug>-architecture/`，例如 `visualization/evo1-architecture/spec.json`。HTML 应内嵌浏览所需资源，单独复制仍可离线打开；用户指定路径或已有页面原位修改时遵循其位置。以下命令中的 `model-name` 需替换成实际模型名。

先选择渲染方式。有高质量参考页时，直接沿用其绘图函数与页面布局；新页面也可手工编写适合模型的紧凑 SVG。下面的 spec 模板是可选兼容方案，不是默认视觉标准，更不能为了使用构建器而重建已有好布局。

采用声明式方案时，可复制 [assets/explorer.html](assets/explorer.html)，按 [references/page-spec.md](references/page-spec.md) 填写模型 spec，然后使用标准库构建工具：

```bash
python <skill-dir>/scripts/build_explorer.py \
  --repo /absolute/model/repo \
  --spec /absolute/model/repo/visualization/model-name-architecture/spec.json \
  --output /absolute/model/repo/visualization/model-name-architecture.html
```

模板是可适配的起点，支持关键参数、机制公式、实现要点、张量追踪和显式前向步骤；新建完整页面时，按实际源码填写这些内容，不只填写最小的 modules / views。允许根据既有项目调整样式、布局和交互。若修改模板，放到目标项目中并通过 `--template` 指定；不要为单个仓库修改已安装 skill 的共享模板。

模板支持视图 `parent` 分级导航、`variant: "operator"` 算子排版、`heading` / `description` 和按视图显示的 `layerControls`。这些能力用于承载已设计好的计算图，不会自动把摘要模块细化为算子。字段用法见 page-spec。

构建器会检查视图 / 模块引用和布局边界，只读取 spec 明确引用的源码文件，用 Python AST 提取定义的真实行号，再将 spec 和源码快照嵌入一个 HTML。它不会自动发现模型结构，也不会证明图中数学关系正确；这些判断必须通过读代码完成。

- 为主要阶段建立 `文件 + 类/方法` 映射，显示原始行号。链接到可阅读的源码快照，避免依赖浏览器打开服务器绝对文件路径。
- 数学关系使用正规 LaTeX；形状、层路径、参数值和算子序列优先用等宽文字，例如 `[B,N,256]`、`256 → 1024 → 256`，不要全部写成花体集合与上标。图中只保留决定计算关系的短公式，完整展开式放进详情；同一公式不在主图、检查器和解释卡中重复堆放。
- 数学渲染按需求选择：任意动态公式可保留 KaTeX；公式集合固定且需要稳定离线显示或独立 SVG 导出时，优先考虑 [compact-diagrams.md](references/compact-diagrams.md) 的预编译路径，构建器可用 `--math-svg` 接入。图、正文和弹窗都可复用同一缓存。不要用普通字符拼出上下标和复杂分式，或缩小字号来代替正规排版；长推导拆开或移入详情。
- 选用离线快照时，嵌入 JSON 中的 `<` 要转义，避免源码中的 `</script>` 截断页面。不要嵌入权重、数据集或无关仓库内容。
- 明确 SVG 的 `viewBox`、导出宽高与背景；长图导出不能沿用整体图的小尺寸。模型源码或配方改变后，重新核对 spec，再重建；刷新快照不会自动修正图形。

已有网页可直接按以上契约改造，不必迁移到模板。优先新增可审阅的可视化文件，保持模型训练 / 推理代码不受影响。

## 验证用户实际操作

使用可用的浏览器工具；本地安装了 Playwright 时也可用它。围绕真实行为验证：

1. 通过用户将访问的 HTTP 地址加载页面；离线作为交付目标时也检查 `file://`。确认渲染后的图和控制台，而非只检查 HTML 文件存在。
2. 实际点击“整体模块 → 内部细图 → 算子详情 → 对应源码”，检查视图确实变化、弹窗可见、正确符号与行号被显示；测试关闭 / 返回，不能只断言右侧文字变了。
3. 检查配置和层号切换后的实例、形状、残差策略。核对 SVG 标签没有超出图框、主要文字不溢出算子框，以及导出文件尺寸。
   有公式时，检查实际字形，不只检查渲染器生成了 DOM：分式、根号、上下标、矩阵、正文、动态图与弹窗均需覆盖。公式按实际高度排列，避免固定行距造成标题碰撞；移动端长公式在局部容器滚动。原生 SVG 还需检查公式与同节点其他文字的碰撞，并独立打开导出文件验证字形路径。
4. 按页面功能检查键盘、移动端与相关控制。只验证任务实际提供的功能；不必为纯文档网页运行模型训练测试。
5. 查看真实截图，至少覆盖总览、内部图、算子详情和手机布局。有参考页时，在相同视口、模型配置和展开位置下对照图高、空白、公式大小及阅读路径。检查关键关系是否保留，也检查是否展开过度：大间距的 LN / Linear / Add 长链、反复打印不变形状、相同内容在多个面板重复，都应先压缩。自动化通过不能作为视觉质量合格的依据。

模板生成的页面可直接运行附带的可选 Playwright 检查器（已有自定义页面的 DOM 不一定适用）：

```bash
python <skill-dir>/scripts/check_explorer.py --page /absolute/model/repo/visualization/model-name-architecture.html
python <skill-dir>/scripts/check_explorer.py --url http://127.0.0.1:8765/model-name-architecture.html --screenshot /absolute/model/repo/visualization/model-name-architecture/preview.png
```

它验证每个配置、节点的实际下钻或弹窗、返回、源码范围、导出尺寸、文字边界、键盘激活与移动端点击。它不判断模型的数学语义，也不覆盖项目后来新增的专用控件；这些需要按上述要点另行验证。

浏览器验证不可用时，完成静态检查并明确未验证的部分；不要声称交互已通过。用户反馈公式有问题时，先复现其实际页面，检查图、正文、弹窗和导出使用的渲染方式、字形、字号及容器裁切；若是普遍问题，修复共享渲染或布局并遍历全部公式。必要时比较服务返回内容与本地文件摘要，不能默认归因为缓存。

## 交付与访问

交付时直接提供模型架构 HTML 的可点击链接，链接文字包含模型名；无需让用户先进入目录查找页面。使用 HTTP 预览时，链接必须包含实际 HTML 文件名，并以这个完整地址进行验证。说明最有价值的展开路径、已验证项，以及任何推导假设。远程服务器上的 `localhost` 属于服务器；若用户需要访问指导，按其连接方式给出端口转发或下载单文件的方法，不把远程绝对文件链接说成一定能在本机浏览器打开。

若启动本地预览服务，先确认端口 / 服务目录，使用任务环境已有的服务管理方式，不中断无关进程。交付时可保存一张实测点击效果图，帮助读者确认界面状态。不要把 TurboVLA 的层数、维度、动作头或目录当成其他模型的默认值。
